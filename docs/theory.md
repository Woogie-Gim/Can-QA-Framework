# CAN 통신 QA 자동화 - 이론 정리

## 1. CAN 통신이란

### 기본 개념

CAN(Controller Area Network)은 차량 내부 ECU들이 서로 통신하기 위해 사용하는 직렬 통신 프로토콜이다. 1986년 보쉬가 개발했고 현재 거의 모든 양산 차량에 적용되어 있다.

핵심 특징은 **브로드캐스트 방식**이라는 점이다. 송신 노드가 특정 수신자를 지정하지 않고 메시지에 ID를 붙여 버스 전체에 뿌리면 그 정보가 필요한 노드가 골라서 받는다. 차속 정보 하나를 계기판과 IVI와 ADAS 모듈이 동시에 사용하는 구조가 이 방식으로 가능해진다.

주소 개념이 없기 때문에 노드를 추가하거나 제거해도 나머지 노드의 설정을 바꿀 필요가 없다. 배선도 두 가닥(CAN High, CAN Low)이면 충분해 차량 내 배선 무게와 비용을 크게 줄인다.

### 프레임 구조

QA 관점에서 알아야 할 요소는 세 가지다.

| 요소 | 설명 |
|---|---|
| ID | 메시지 식별자. 표준 11비트 또는 확장 29비트. 값이 작을수록 우선순위가 높다 |
| DLC | 데이터 길이. 0~8바이트 (CAN FD는 최대 64바이트) |
| Data | 실제 신호가 담기는 영역 |

ID는 "누가 보냈는가"가 아니라 "무슨 내용인가"를 나타낸다. 0x100이 차량 상태 정보라면 그것을 보내는 노드가 무엇이든 수신 측은 0x100을 차량 상태로 해석한다.

우선순위 방식도 특이하다. 두 노드가 동시에 송신하면 ID가 낮은 쪽이 이기고 진 쪽은 자동으로 재시도한다. 충돌로 인한 데이터 손실이 없어 실시간성이 요구되는 차량 환경에 적합하다.

### 주기 전송

대부분의 CAN 신호는 이벤트가 아니라 **일정 주기로 반복 전송**된다. 차속은 10ms, 도어 상태는 200ms 같은 식이다.

이 특성이 QA에서 중요한 이유는 두 가지다.

- 주기가 어긋나는 것 자체가 결함이다. 값이 정확해도 규격 주기를 벗어나면 수신 측 제어 타이밍이 깨진다
- 주기 전송을 전제로 수신 측이 타임아웃을 판단한다. 100ms 주기 신호가 500ms 동안 안 오면 송신 노드에 문제가 생겼다고 판단하고 폴백 동작에 들어간다

### 안전 장치: 롤링 카운터와 체크섬

안전 관련 신호에는 두 가지 보호 장치가 함께 실린다.

**롤링 카운터(Alive Counter)** — 매 전송마다 0→1→2 순으로 증가하고 최대값에서 0으로 돌아간다. 수신 측은 이 값이 변하지 않으면 송신 측이 정지했거나 과거 값이 반복 전송되고 있다고 판단한다. **값 자체는 정상 범위인데 통신은 죽어 있는 상황**을 잡아내는 장치다.

**체크섬** — 데이터가 전송 중 변조되지 않았는지 확인한다. 송신 측이 계산해 붙이고 수신 측이 다시 계산해 비교한다.

이 둘은 CAN 프로토콜 자체의 기능이 아니라 데이터 영역 안에 별도 신호로 정의해 사용하는 애플리케이션 레벨 규약이다.

## 2. DBC 파일

### 역할

CAN 버스에 흐르는 것은 바이트 나열일 뿐이다. `04 B0`이 무엇을 의미하는지는 프로토콜이 알려주지 않는다.

DBC(Database CAN)는 이 해석 규칙을 정의한 명세 파일이다. 어떤 ID의 몇 번째 비트부터 몇 비트가 어떤 신호이며 그 값을 어떻게 실제 단위로 환산하는지가 적혀 있다.

**QA 관점에서 DBC는 요구사항 명세서다.** 실무에서 완성차 업체가 DBC를 배포하고 협력사가 그에 맞춰 구현한다. 검증 담당자는 "구현이 이 명세를 지켰는가"를 판정하며 그 판정 기준이 전부 DBC에서 나온다.

### 문법

```
BO_ 256 VehicleStatus: 8 GATEWAY
 SG_ VehicleSpeed : 0|16@1+ (0.1,0) [0|255] "km/h" IVI
```

**BO_ 줄 (메시지 정의)**

| 항목 | 값 | 의미 |
|---|---|---|
| ID | 256 | 메시지 ID. **10진수로 표기** (0x100) |
| 이름 | VehicleStatus | 메시지 이름 |
| DLC | 8 | 데이터 길이 |
| 송신 노드 | GATEWAY | 이 메시지를 보내는 노드 |

**SG_ 줄 (신호 정의)** — 앞에 공백 한 칸이 반드시 필요하다

| 항목 | 값 | 의미 |
|---|---|---|
| 비트 위치 | 0\|16 | 0번 비트부터 16비트 사용 |
| 바이트 순서/부호 | @1+ | 1은 리틀엔디안, +는 부호 없음 |
| 스케일·오프셋 | (0.1,0) | 실제값 = 원시값 × 0.1 + 0 |
| 유효 범위 | [0\|255] | 최소값과 최대값. **테스트 케이스의 근거** |
| 단위 | "km/h" | 표시 단위 |
| 수신 노드 | IVI | 이 신호를 사용하는 노드 |

### 스케일과 오프셋이 존재하는 이유

CAN 데이터 영역은 최대 8바이트로 매우 좁다. 소수점을 그대로 담을 수 없으므로 정수로 변환해 전송하고 수신 측이 되돌린다.

차속 120 km/h를 0.1 단위로 표현하면 1200이 되고 이를 2바이트 16진수로 쓰면 `04 B0`이다. 버스에는 이 바이트가 흐르고 DBC를 거치면 다시 120.0이 된다.

이 변환 규칙을 코드에 하드코딩하면 스펙이 바뀔 때마다 코드를 고쳐야 하고 무엇보다 **검증 기준이 검증 대상 안에 들어가 버린다.** DBC로 분리하는 이유가 여기 있다.

## 3. CAN 기반 QA의 구조

### 테스터의 두 가지 역할

**관찰자 (Monitoring)**

버스에 흐르는 메시지를 수신해 규격 준수 여부를 판정한다. 주기가 맞는지, 값이 유효 범위 안인지, DLC가 규격대로인지를 본다.

**가짜 ECU (Restbus Simulation)**

실제 차량 없이 IVI 단품만 놓고 테스트할 때 나머지 ECU가 전부 없다. 이때 테스트 장비가 그 없는 ECU들을 흉내내 신호를 생성한다. 차속 120을 주입하면 IVI 속도계가 120을 표시하는가, 기어를 R로 넣으면 후방 카메라 화면이 뜨는가를 검증한다.

이것을 **레스트버스 시뮬레이션**이라 부르며 IVI 평가 업무의 상당 부분을 차지한다. 하드웨어가 없어 임시로 만든 방식이 아니라 실무의 표준 검증 방식이다.

### 실무 도구

| 도구 | 성격 |
|---|---|
| Vector CANoe / CAPL | 업계 표준 상용 도구. 시뮬레이션과 분석 통합 |
| SocketCAN + can-utils | 리눅스 커널 내장 CAN 스택. candump, cansend 등 |
| python-can + cantools | 오픈소스 파이썬 라이브러리. CI 연동에 유리 |

CANoe는 라이선스 비용 문제로 개인이 접근하기 어렵다. python-can 생태계는 동일한 구조를 오픈소스로 구현할 수 있고 CI 파이프라인에 붙이기 쉬워 자동화 QA 영역에서 실제로 사용된다.

## 4. 프로젝트 설계

### 전체 구조

```
[가상 ECU 시뮬레이터]  ← 결함 주입 옵션
         ↓ CAN 프레임
      [vcan0 버스]
         ↓
   ┌─────┴─────┐
   ↓           ↓
[수집기]   [IVI 대시보드]
   ↓           ↓
[검증 엔진] [화면 캡처·판정]
   ↓
[엑셀 리포트]
                    ↑
              [DBC 명세] 를 모두가 참조
```

### 설계 원칙

**명세와 구현의 분리**

시뮬레이터와 검증 엔진이 각각 DBC를 참조한다. 테스트 코드에 `assert value <= 8000` 같은 숫자를 직접 쓰지 않고 DBC에서 읽어온 값과 비교한다. 스펙이 변경되면 DBC만 수정하면 테스트가 자동으로 따라온다.

**하드웨어 독립 설계**

버스 연결을 별도 계층으로 분리했다. 채널 설정만 vcan0에서 실제 can0으로 바꾸면 물리 CAN 인터페이스에 그대로 연결된다. 가상 환경에서 개발했으나 실장비 전환이 설계에 반영되어 있다.

**SUT와 테스트 도구의 분리**

시뮬레이터는 검증 대상이고 테스트는 검증 주체다. 두 프로세스를 분리해 실행하며 서로의 내부 상태를 공유하지 않는다. 오직 CAN 버스만을 통해 상호작용한다.

### 검증 항목

| 항목 | 검증 내용 | 근거 |
|---|---|---|
| 메시지 수신 | 규격 메시지가 버스에 존재하는가 | DBC 메시지 정의 |
| 주기 준수 | 송신 간격이 규격 범위 내인가 | 100±20ms |
| 신호 범위 | 값이 유효 범위를 벗어나지 않는가 | DBC minimum/maximum |
| 롤링 카운터 | 매 프레임 1씩 증가하는가 | 0~15 순환 |
| 화면 반영 | CAN 신호가 UI에 정확히 표시되는가 | OCR 및 픽셀 판정 |

## 5. 결함 주입과 테스트 유효성

### 왜 일부러 고장을 내는가

테스트가 전부 통과했다는 결과는 두 가지 해석이 가능하다.

1. 시스템이 실제로 정상이다
2. 테스트가 아무것도 검증하지 못하고 있다

두 경우 모두 초록불이 켜지며 결과 화면만으로는 구분할 수 없다. 조건을 잘못 작성한 테스트는 반복문이 한 번도 실행되지 않은 채 통과하기도 한다.

따라서 **답을 아는 문제를 의도적으로 주입해 검출 여부를 확인**해야 테스트를 신뢰할 수 있다. 이 개념은 소프트웨어 공학에서 뮤테이션 테스팅으로 체계화되어 있다.

### 주입한 결함과 검출 결과

| 결함 | 주입 방식 | 검출 테스트 | 실측 |
|---|---|---|---|
| 정상 | - | - | 7 passed |
| 롤링 카운터 고정 | AliveCounter를 3으로 고정 | 카운터 연속성 | 3 다음 3 수신 |
| 신호 범위 초과 | EngineRPM 9000 주입 | 신호 범위 | 규격 [0,8000] 이탈 |
| 주기 지연 | 송신 주기 100→300ms | 주기 준수 | 평균 297.0ms |
| 메시지 미전송 | 송신 중단 | 메시지 수신 | 프레임 0건, 나머지 SKIP |

각 결함이 의도한 테스트에서만 검출되고 나머지 항목은 정상 통과하는 것을 확인했다. 이는 테스트 케이스 간 독립성이 확보되었음을 의미한다.

### 검증 실패와 검증 불가의 구분

메시지 미전송 조건에서 초기 구현은 7개 항목이 모두 오류로 처리되었다. 그러나 실제로 문제인 것은 "메시지가 오지 않는다" 하나이며 나머지는 판정할 데이터가 없어 실행되지 못한 것이다.

이를 FAIL과 SKIP으로 분리했다. 리포트에 모든 항목이 실패로 기록되면 원인 분석 시 무엇이 실제 결함인지 식별할 수 없기 때문이다.

## 6. 개발 과정에서 발견한 문제

### 결함 주입 시 테스트 간 간섭

**현상** — 신호 범위 초과 결함을 주입했는데 주기 검증 테스트까지 실패했다.

**원인** — 범위를 벗어난 값을 인코딩할 때 예외가 발생하고 이를 포착해 재시도하는 과정에서 송신 타이밍이 밀렸다. 결함 하나가 무관한 특성까지 오염시킨 것이다.

**조치** — 예외가 발생하지 않는 인코딩 방식으로 변경했다. 이후 각 결함이 대응하는 테스트만 실패한다.

### 주기 검증의 간헐적 실패

**현상** — 동일한 정상 조건에서 주기 테스트가 통과와 실패를 반복했다. 실측값이 121~125ms로 허용 범위 경계에 걸쳤다.

**원인** — `sleep`은 지정 시간 이상 대기함을 보장할 뿐 정확한 간격을 보장하지 않는다. 여기에 인코딩과 송신 처리 시간이 매 주기 누적되었다.

**조치** — 목표 시각을 기준으로 대기 시간을 계산하는 방식으로 변경해 처리 시간이 누적되지 않도록 했다. 이후 주기 검증이 안정적으로 통과한다.

**의의** — 허용 오차를 넓혀 통과시키는 방식도 가능했으나 이는 검증 기준을 완화해 문제를 은폐하는 것이므로 채택하지 않았다.

## 7. 면접 예상 질문

**Q. 테스트가 유효한지 어떻게 확인했는가**

결함 5종을 정의하고 각각 주입해 의도한 테스트에서만 검출되는지 확인했다. 테스트가 통과한다는 사실만으로는 그 테스트가 실제로 검증을 수행하는지 알 수 없기 때문이다. 검출 결과를 조건별 리포트로 남겨 근거를 확보했다.

**Q. 실제 하드웨어 없이 검증한 것의 한계는**

물리 계층 특성을 검증할 수 없다. 종단 저항 문제, 버스 부하율, 전기적 노이즈로 인한 오류 프레임, 비트 타이밍 오차 등은 가상 인터페이스에서 재현되지 않는다. 다만 신호 레벨 이상의 애플리케이션 검증은 동일하게 수행 가능하며 버스 연결 계층을 분리 설계해 실장비 전환 시 코드 수정 범위를 최소화했다.

**Q. CANoe를 사용해 본 경험이 있는가**

상용 도구 경험은 없으나 python-can으로 동등한 구조를 직접 구현했다. 레스트버스 시뮬레이션, 신호 인코딩·디코딩, 주기 검증, 결함 주입에 이르는 흐름을 설계 수준에서 이해하고 있으며 CAPL로의 전환은 문법 습득 문제라고 판단한다.

**Q. 이 프로젝트에서 QA다운 부분은 무엇인가**

세 가지다. 판정 기준을 DBC로 분리해 검증 대상 외부에 두었고, 합격 판정을 자동화해 사람의 눈 확인을 제거했으며, 결함 주입으로 검증 도구 자체의 유효성을 확인했다. 세 번째가 개발과 QA를 가르는 지점이라고 본다.

**Q. 확장한다면 어느 방향인가**

세 가지를 고려한다. 첫째로 체크섬 검증 추가. 현재는 롤링 카운터만 확인하고 있다. 둘째로 차량 이더넷과 SOME/IP 대응. 최신 IVI는 CAN 외 통신도 사용한다. 셋째로 CI 파이프라인 연동. 야간 자동 실행 후 리포트를 배포하는 형태로 확장 가능하다.

## 8. 용어 정리

| 용어 | 설명 |
|---|---|
| CAN | 차량 내 ECU 간 통신 프로토콜 |
| ECU | Electronic Control Unit. 차량 내 전자 제어 장치 |
| IVI | In-Vehicle Infotainment. 차량용 인포테인먼트 시스템 |
| DBC | CAN 신호 정의 명세 파일 |
| SocketCAN | 리눅스 커널의 CAN 프로토콜 스택 |
| vcan | 가상 CAN 인터페이스. 하드웨어 없이 동작 |
| 레스트버스 시뮬레이션 | 부재한 ECU들을 대신해 신호를 생성하는 검증 기법 |
| 롤링 카운터 | 매 전송마다 증가하는 신호. 통신 생존 확인용 |
| DLC | Data Length Code. 프레임의 데이터 길이 |
| SUT | System Under Test. 검증 대상 시스템 |
| 결함 주입 | 의도적으로 이상 상태를 만들어 검출 여부를 확인하는 기법 |
